## 1. Миграция i18n — закончена

Было 466 тернарников, стало 0. Единственное оставшееся `lang === "ru"` — это
переключатель языка в `src/app/hooks/useLanguage.js`, и он там уместен.

Прошлая редакция этого документа заявляла ноль преждевременно: в
`ResolveModal` оставались четыре штуки. Их не поймал счётчик, потому что они
были написаны как `isRu ?`, а не `lang === "ru"` — искать стоит обе формы.
Режим «в ремонте» переопределял четыре подписи из десяти, теперь они лежат в
`resolve.repair`, а сам компонент выбирает префикс ключа.

Новые namespace: `app`, `cards`, `common`, `excelExport`, `importConflict`,
`leakForm`, `localSync`, `priority`, `pwa`, `reopen`, `userProfile`.

Что стоит знать тому, кто будет добавлять строки:

- **Тесты берут перевод из настоящей локали.** Мок `useLanguage` — это
  `englishLanguageHook()` из `@/test/translate`; для кода, который должен
  работать на обоих языках, есть `translateRu`. Пропажа ключа валит тест.
- **Не всё, что ветвится по языку, — перевод.** `lang === "ru" ? "ru-RU" : "en-US"`
  это Intl-локаль, для неё есть `getIntlLocale` в `src/utils/locale.js`.
- **Множественное число.** У русского три формы там, где у английского две.
  `ImportConflictSheet` выбирает форму через `Intl.PluralRules`, а локаль хранит
  все формы, которые язык умеет выбрать. Так страж паритета остаётся строгим
  сравнением множеств ключей — суффиксы i18next (`_one`, `_few`) его бы сломали.
- **`t` в зависимостях хуков.** Если эффект вызывает `setState`, а мок в тесте
  отдаёт новый `t` на каждый вызов — бесконечный цикл и смерть воркера **без
  единого упавшего утверждения**: файл просто исчезает из прогона. Проверять
  число тестов, а не только «passed».

### Выбор объекта — новая функция

Кнопка с текущим путём в шапке открывает навигацию по локациям как по папкам:
`Подразделение → Месторождение → Локация` (и эквиваленты для midstream и
downstream). Выбранная папка задаёт область работы для Базы, Карты и
Мониторинга. Задумано как замена перебору фильтров, когда записей тысячи.

Область не хранится отдельной сущностью — это те же три фильтра локации,
прочитанные обратно как путь. Отсюда следует, что:

- проводник и чекбоксы в Базе не могут разойтись — это одно состояние;
- выбор переживает перезагрузку и переключение проекта бесплатно, потому что
  фильтры уже сохранялись;
- фильтр, заданный чекбоксами в несколько значений, — не путь. Шапка показывает
  «Выбрано несколько», а не одно из значений: соврать про остальные хуже, чем
  признать, что пути нет.

Третий уровень (`lastLocationFilter`) добавлен в схему сохранения. Старые
записи фильтров его не содержат, что нормализуется в `null` — иначе апгрейд
скрыл бы все утечки, которым отсутствующий фильтр не соответствует; на это есть
отдельный тест.

`useAppBootstrap` при этом уменьшился с 542 строк до 429: блок фильтров уехал в
`useSharedFilters`. Не косметика — бюджет `check:maintainability` не пропустил
рост файла, и это ровно то, ради чего он стоит. Потолок в
`maintainability-budget.json` опущен следом, как требует его же политика.

Чекбоксы локаций убраны из обоих мест, где они были, — из фильтр-панели Базы и
Мониторинга и из листа Карты. Они писали в те же три фильтра, что и проводник,
то есть дублировали логику и могли разойтись с ним. Выбор папки теперь
открывает Базу с её содержимым; «Показать все» — это выход из папки, а не
запрос открыть весь проект, поэтому экран не меняет.

Область распространена и на Главную: сводка по статусам, список последних
записей и кнопка «Показать все» считаются по выбранной папке. У кнопки это
заметно вдвойне — она ведёт на Базу, которая уже сужена, так что счёт по
всему проекту обещал бы записи, которых тот экран не покажет; при папке
меньше восьми записей кнопка просто не нужна и не появляется. Заодно на неё переведён счётчик на кнопке
«База» — он ведёт на экран, который уже сужен, так что счёт по всему проекту
противоречил бы списку, на который пользователь попадает.

**Здесь была ловушка, стоящая отдельного упоминания.** `useMainPageActions`
получает `data` и на каждое изменение собирает новый массив из него, отдавая в
`setData`. Передай туда сокращённый список — и первое же сохранение утечки
удалило бы все записи вне выбранной папки, молча, а заметно это стало бы только
после перезагрузки. Поэтому хук принимает два списка: `data` для записи и
`scopedData` для показа. То же касается `deletePhotoIfUnreferenced` — он ищет
ссылки на фото по всему проекту, иначе удалил бы файл, на который ссылается
утечка за пределами области.

На это есть тесты, и они проверены мутацией: подмена `data` на `scopedData` в
обработчике сохранения валит их с `expected [ 'leak-1' ] to deeply equal
[ 'leak-1', 'leak-2' ]`. Плюс e2e, который правит утечку внутри папки, сбрасывает
область и убеждается, что в проекте по-прежнему три записи.

**Чтения из хранилища по области не будет без смены схемы.** Просьба «читать
базу только по выбранной папке» упирается в то, как устроено хранение: payload
проекта лежит **одной записью** в IndexedDB (`{ id: projectId, data }`,
`webProjectEnvelopeStore.js`), без отдельных записей на утечку и без индексов по
полям локации. Прочитать часть нельзя — `get()` возвращает весь массив, и
structured clone всего массива оплачивается в любом случае. Чтобы это стало
возможным, потребовалось бы хранить утечки отдельными записями с индексом по
полю локации, что затрагивает импорт, экспорт, бэкап, синхронизацию и проверку
целостности — то есть всё, что сейчас читает и пишет снапшот целиком.

Отдельно стоит заметить, что выигрыш был бы неполным: проводник показывает
число утечек в каждой папке, а для этого всё равно нужны все записи — пусть и
только их поля локации. Это решается отдельным лёгким индексом, но это уже
вторая часть той же работы.

### Ветки конфликта Excel-импорта — закрыты в e2e

Из трёх исходов конфликта («Проект уже существует») браузерным тестом была
покрыта только «Создать копию» — самая безобидная: она ничего не трогает.
`e2e/excel-conflict.spec.js` добавляет две оставшиеся, те, где регрессия теряет
данные:

- **Перезаписать** — архив выгружается, после чего утечка локально переводится
  «в ремонт». Перезапись обязана вернуть состояние архива, то есть
  проигнорировать более свежую локальную правку; иначе ветка неотличима от
  слияния.
- **Объединить** — вторая утечка заводится уже после выгрузки, поэтому в архиве
  её нет. Счётчики листа конфликта (`Добавится 0`, `Пропустится 1`) остались бы
  верны и при потере локальной записи, так что проверяется другое: обе утечки
  переживают импорт и перезагрузку.

Оба случая построены так, что ожидаемый результат не зависит от таймстампов
слияния: расхождение создаётся после экспорта.

Общие шаги вынесены в `e2e/helpers.js` — `app.smoke.spec.js` держал их у себя,

### Двойная распаковка архива — сделано

Было: `verifyArchiveLimits` распаковывал каждый файл архива целиком, чтобы
сложить фактические размеры, после чего тот же файл распаковывался второй раз
при реальном чтении.

Стало: на ZIP-путях (`parseExcelZip`, `parseBackupZip`) остался дешёвый
преflight по заголовкам (`assertArchiveLimits`), а фактические байты считает
`readArchiveEntry` — во время того чтения, которое импорту нужно в любом случае.
Бюджет общий на архив (WeakMap по экземпляру JSZip), лимиты те же.

Гарантия сохранена: байты считаются по мере выдачи декомпрессором, поэтому
подделанный `uncompressedSize` по-прежнему не даёт обойти лимит. Изменился
момент отказа — не до старта импорта, а на проблемной записи. Записи, которые
импорт не читает, теперь не распаковываются вовсе.

`parseExcelLeaks` намеренно оставлен на `verifyArchiveLimits`: там книгу
распаковывает сам ExcelJS, инструментировать его чтение нечем.

Замер на архиве 12 МБ (12 фото, Node/jsdom): 23 мс → 15 мс. На Android с
большим числом фото выигрыш должен быть заметнее, но там не мерялось.

### Web Worker для импорта — сделано

Экспорт и импорт делят один `src/services/excel/excel.worker.js`: два воркера
означали бы вторую копию ExcelJS, около 900 кБ.

Бэкап-импорт переехал последним. Фото не возвращаются пачкой — архив остаётся
открытым внутри воркера, а главный поток запрашивает их по мере сохранения,

`parseBackupZip` больше не отдаёт живой JSZip — только ридер, поэтому результат

загрузился, ответ не клонируется, таймаут). Архив, отвергнутый по существу,
второй раз не разбирается.

## 5. Мелочи

### CRC32 при экспорте — мерялся, решено не трогать

`updateCrc32()` в `src/services/archive/zipStoreStream.js:22` обходит буфер
побайтово. Основную оптимизацию тут уже сделали (отказ от `for...of` в пользу
индексного цикла, ~40 %).

Следующий шаг — slice-by-8 (восемь таблиц, по 8 байт за итерацию). Прототип
сверен с текущей реализацией на 200 случайных буферах, результат совпадает;
на 16 МБ даёт **41 мс → 32 мс, всего 1.28×**.

Это ~10 мс на 16 МБ в функции, от корректности которой зависит целостность
архива, ценой восьми таблиц и развёрнутого цикла. При действующем бюджете
поддерживаемости размен невыгодный. Возвращаться, если появятся жалобы именно
на скорость экспорта больших проектов, — и тогда лучше сразу считать CRC в
воркере, а не ускорять цикл.

Запас ~12 КБ. Локали лежат в ленивых чанках (`locale-ru` 45 КБ, `locale-en`
32 КБ), поэтому ни миграция i18n, ни новые ключи бюджет не съели. Следующая
заметная фича в initial-графе уронит CI.

Граф Excel-воркера — 1 145 907 / 1 179 648 (97,1 %). Порог перекалиброван,
когда воркер взял на себя разбор импорта: вместе с парсером туда пришла своя
копия JSZip (~97 кБ), без которой распаковку с главного потока не убрать.
Классификатор в `check-bundle-budget.mjs` эту копию раньше не считал и занижал
граф воркера, завышая граф приложения на те же 97 кБ.

### Мажорные версии — подняты, кроме сборочной цепочки

Подняты: `i18next` 23 → 26 и `react-i18next` 13 → 17 (блокер снят вместе с
концом миграции; правок не потребовалось), `web-vitals` 2 → 6,
`@testing-library/jest-dom` 6 → 7, `jsdom` 29 → 30, `lint-staged` 16 → 17.

`web-vitals` единственный потребовал кода: в v3 метрики переименованы из `getX`
в `onX`, в v4 `FID` удалён в пользу `INP`. Заодно отчёт переехал в динамический
импорт — в стартовом чанке ему не место, и это окупило рост от обеих
i18n-библиотек: initial gzip 122 633 против 123 152 до всей серии.

**Не подняты, и это не бампы:**

- **Vite 6 → 8.** В восьмой версии сборка переехала на rolldown, который не
  принимает объектную форму `manualChunks` — только функцию. Значит меняется и
  разбиение на чанки, а вместе с ним основания всех размерных бюджетов и
  классификатор в `check-bundle-budget.mjs`, который опознаёт чанки по именам.
  Это отдельная ветка с перекалибровкой бюджетов, а не строчка в package.json.
- **TypeScript 6 → 7.** Строже к `new Promise` без явного `void` (пять мест) и
  к вызовам без аргументов в `LeakDetailsSheet` (пять мест). Правки типов
  механические, но их десяток, а выгоды в рантайме ноль: TypeScript здесь
  только проверяет типы, ничего не собирая. Делать вместе с Vite или отдельно,
  но не в общей череде обновлений.

### Дублирование порогов покрытия — сделано

Пороги лежали **в двух местах**: `vite.config.mjs` (`coverage.thresholds`) и
`scripts/coverage-ratchet.json`, и расходились. Для `useSettingsPage.js` vite
требовал 45/25/40/45, ratchet — 92/58/92/94; для `Settings.jsx` 30/15/30/30
против 68/66/51/68. Слабейший из двух не защищал ничего.

Теперь источник один — `scripts/coverage-policy.json`:

- `global` — общие пороги, `files` — пофайловые полы, `directories` — глобы
  (их проверяет только vitest: ratchet сличает конкретные пути).
- `vite.config.mjs` собирает из него `coverage.thresholds`.
- `check-coverage-ratchet.mjs` читает тот же файл и вдобавок сверяет `total`,
  чего раньше не делал.

При слиянии по каждой метрике взят максимум из двух прежних значений, так что
ни один порог не понизился. Под ratchet попали пять файлов, которых там не
было: `MainPage.jsx`, `DataBase.jsx`, `MapPage.jsx`, `ProjectContext.jsx`,
`useOfflineMapActions.js`.

## 6. Готовность к продакшену

### Блокеры выпуска Android

**Подпись релиза — сделана.** `npm run android:release` прошёл целиком впервые:
собран `app-release.apk`, `versionCode=1`, `versionName=1.0.0`. Отпечаток сверен
с README сравнением строк, а не глазами:

```
b56e337c377ed17a7534e0c86c055f735446e137be7bc8b83713a8d2a47f1527
```

Подпись схемами v2 и v3, один подписант, DN совпадает. APK установлен на
устройство и запускается без исключений.

Шесть переменных окружения задаются вне репозитория; keystore и пароли в
историю не попадали, `.gitignore` по-прежнему отклоняет `*.jks`, `*.keystore`,
`*.p12`.

В цепочку добавлен `check:android-r8` — он читает отчёты R8 после
`assembleRelease` и падает, если из рантайма Capacitor пропали аннотации
плагинов. Без него релиз, в котором камера и геолокация падают по нажатию,
проходил все гейты (см. ниже).

**Instrumented-тесты выполнены — первый раз.** Приложение Android-first —
Filesystem API и локальная Wi-Fi-синхронизация имеют native-половину, а именно
её проверяют instrumented. JS-сторона синхронизации покрыта на 87,5 %,
Kotlin — 84 unit-теста.

Прогон на локальном эмуляторе (`Pixel_9`, arm64, API 37):
`./gradlew :app:connectedDebugAndroidTest` — 15 тестов, 0 падений, 0 ошибок.
Пропущен один, `sqliteStorageMeetsBudgets`: он под `assumeTrue` и требует
`nativeStoragePerformance=true` плюс сборку с
`VITE_ENABLE_NATIVE_STORAGE_PERFORMANCE=true`, так что CI его тоже пропускает.
Пройдено в том числе `localSyncCreatesAndroidKeystoreTlsIdentity` и
`partialTransferFailsClosed` — то самое поведение native-половины, которого
статический сторож не касается.

Оговорка: локальный прогон был на API 37, а матрица CI — 24 и 35. Установить
образы 24/35 локально нечем: в SDK нет `cmdline-tools`, а значит и
`sdkmanager`. API 24 — это `minSdkVersion`, самый рискованный уровень, и
проверен он пока только в CI.

Часть стыка теперь сторожится статически:
`src/services/sync/localSyncNativeContract.test.js` разбирает
`LocalSyncPlugin.java` и `localSyncService.js` и падает, если JS зовёт метод,
которого в плагине нет, или шлёт ключ, который Java не читает. Это ровно то,
что моки поймать не могут: мок реализует всё, о чём его просят, а Capacitor
отдаёт незнакомый метод отказом, а незнакомый ключ — тихим `null`. Проверено
мутацией: подмена `sessionId` на `sessionIdd` валит тест.

Чего этот сторож **не** проверяет: TLS-рукопожатие, пиннинг, работу с
сокетами и файловой системой — то есть всё поведение native-половины. Для
этого по-прежнему нужен эмулятор.

### Процесс

`main` отстаёт на 497 коммитов, его верхушка — «Android APP», «Test», «Commit
changes». Релизный путь целиком ни разу не проходили: всё живёт на
`codex/local-wifi-sync`. Прежде чем выпускать, надо один раз довести коммит до
`main` через CI и увидеть все семь job'ов зелёными — включая те, что локально
не воспроизвести (эмулятор API 24/35, WebKit).

### Веб/PWA

Готов. Все гейты, `verify:release`, e2e и offline-smoke проходят.

Одно требование к развёртыванию вынесено в README («Заголовки, которые обязан
отдавать сервер»): CSP живёт в `<meta>`, а `frame-ancestors`, `report-uri` и
`sandbox` в meta-теге игнорируются по спецификации. Пока сервер не отдаёт
`Content-Security-Policy: frame-ancestors 'none'`, веб-версию можно встроить в
чужой iframe. Там же HSTS, `X-Content-Type-Options`, `Referrer-Policy`
(`no-referrer` — иначе Referer к внешнему тайл-серверу раскрывает адрес
установки) и `Permissions-Policy`.
